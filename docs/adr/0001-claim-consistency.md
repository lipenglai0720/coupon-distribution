# ADR：异步领取、Redis预占与数据库事实

领取接口先在数据库事务中建立 PENDING 请求，再调用 Redis Lua 原子完成库存与单用户配额预占，同时写入 Outbox；接口返回202代表受理。
MySQL事务提交后，Outbox经 RabbitMQ 传递请求编号。消费者依照请求行锁执行：唯一约束、模板库存行锁和订单状态条件是最终正确性保障。
消费者提交 SUCCESS/FAILED 与 Inbox 后才 ACK；Redis预占在数据库提交后标记完成或释放。Lua仅释放仍为R的预占，避免重复回补。

故障窗口与恢复：

- Redis预占后数据库回滚：Redis pending ZSet中留下孤立预占；一分钟后核对数据库不存在的请求，幂等释放。
- 已受理但投递失败：Outbox退避重试，Publisher Confirm及Returns共同确认投递。
- 已投递但消费失败：PENDING请求的定时修复重新激活Outbox；超过5个修复周期则终止并释放预占。
- 已提交但ACK丢失：Inbox及请求状态挡住重复业务变更。
- Redis数据丢失：重建准入库存时，扣除数据库中其他有效PENDING请求；最终发券仍由MySQL约束与库存控制。
- 超时失败后晚到的消息：终态请求不再发券。

本方案保留每次受理的MySQL写入，优先做到结果可查询、故障可恢复。不能把它描述为完全绕过数据库的纯Redis秒杀。API受理与最终到账是两个指标。
缓存用于查询及准入，锁券/核销/退款始终核对数据库状态、关联订单和时间。缓存降级不改变数据库事实。
